# HTTP API

## Загальні правила

- Тіла запитів і відповідей передаються у форматі JSON.
  Відповідь 204 не містить тіла.
- Автентифікація працює через серверну сесію.
  Браузер передає її ідентифікатор у cookie.
- Сервер визначає поточного користувача та його роль.
  Клієнт не задає власника резерву або працівника, який видає товар.
- Каталог і резервування доступні лише після входу.
- Паролі, їхні хеші та внутрішні подробиці помилок БД не повертаються у відповідях.

Помилки повертаються в єдиному форматі:

```json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Неправильний email або пароль"
  }
}
```

code - стабільний код для обробки у фронтенді та тестах.
message - зрозуміле повідомлення для користувача.


## Сесії

- Сесія діє 8 годин від успішного входу.
  Активність не продовжує цей строк.
- Строк дії перевіряється сервером.
  Прострочена сесія не дає доступу навіть за наявності cookie.
- Успішний вхід створює новий ідентифікатор сесії.
  Попередня сесія цього браузера, якщо вона була, завершується.
- Невдала перевірка email або пароля не змінює чинну сесію.
- Вихід завершує поточну сесію, не зачіпаючи інші пристрої.

Cookie сесії:
- HttpOnly - недоступна для читання через JavaScript;
- SameSite=Lax;
- Path=/;
- Secure - увімкнено для HTTPS;
  для локальної розробки через HTTP вимкнено.

## Захист запитів від CSRF

Вебінтерфейс і API працюють на одному origin.

Для всіх POST-запитів, включно з входом і виходом,
сервер перевіряє заголовок Origin до виконання операції.

Дозволений origin задається конфігурацією застосунку.
Значення має точно збігатися за протоколом, хостом і портом.

Відсутній Origin, значення null або невідповідність:
403 / CSRF_ORIGIN_REJECTED. Операція не виконується.

Для GET-запитів ця перевірка не потрібна:
вони не виконують бізнес-операцій, які змінюють дані.

Перевірка Origin не замінює перевірку сесії та прав.
## Автентифікація

### POST /auth/login

Доступ: без попереднього входу.

Тіло запиту:
- email - email користувача;
- password - пароль.

Успіх: 200.
Повертаються id, name, email, role.
Сервер створює нову сесію та встановлює cookie.

Помилки:
- 400 - відсутні поля або неправильний формат;
- 401 - неправильний email або пароль;
- 503 - недоступне сховище користувачів або сесій.

Для невідомого email і неправильного пароля повертається
однакове повідомлення: «Неправильний email або пароль».

### GET /auth/me

Доступ: чинна сесія.

Успіх: 200.
Повертаються id, name, email, role поточного користувача.

Помилки:
- 401 - сесія відсутня, прострочена або завершена;
- 503 - недоступне необхідне сховище.

### POST /auth/logout

Сервер завершує поточну сесію та очищає cookie.

Успіх: 204, без тіла відповіді.
Якщо сесія вже відсутня або завершена, також повертається 204.

Помилки:
- 503 - через збій сховища неможливо завершити сесію.

Після успішного виходу стара cookie не дає доступу.

## Каталог

### GET /products

Доступ: користувач або працівник із чинною сесією.

Тіло запиту: відсутнє.

Успіх: 200.
Повертається масив товарів, відсортований за id за зростанням.

Поля товару:
- id - ідентифікатор;
- articleCode - артикул;
- name - назва;
- desc - опис;
- available - доступна кількість: onHand - reserved.

Приклад відповіді:

```json
[
  {
    "id": 1,
    "articleCode": "ITEM-001",
    "name": "Клавіатура",
    "desc": "Дротова USB-клавіатура",
    "available": 8
  }
]
```

Товари з available = 0 також повертаються.
Якщо каталог порожній, повертається 200 та порожній масив [].

Помилки:
- 401 / UNAUTHENTICATED - немає чинної сесії;
- 503 / SERVICE_UNAVAILABLE - недоступне необхідне сховище.

Перегляд каталогу не змінює залишки.
Доступна кількість у відповіді не гарантує успішного резервування:
сервер повторно перевіряє її під час створення резерву.

## Резервування

### POST /reservations

Доступ: користувач із роллю USER та чинною сесією.
Працівник не може створювати резерви.

Заголовки:
- Idempotency-Key - обов’язковий непорожній рядок,
  не більше 128 символів.

Тіло запиту:
- productId - додатний цілий числовий ідентифікатор товару;
- quantity - додатна ціла кількість одиниць товару.

productId, quantity та id резерву в URL мають бути в діапазоні
1–2 147 483 647 включно. Перевищення межі повертає 400 / VALIDATION_ERROR.

Приклад запиту:

```json
{
  "productId": 1,
  "quantity": 3
}
```

Власник визначається за сесією.
Початковий статус ACTIVE і час створення встановлює сервер.
Поля, крім productId та quantity, у тілі запиту не допускаються.

#### Успішне створення

Статус: 201.

Приклад відповіді:

```json
{
  "id": 15,
  "userId": 2,
  "productId": 1,
  "quantity": 3,
  "status": "ACTIVE",
  "createdAt": "2026-10-17T12:00:00.000Z",
  "closedAt": null,
  "issuedById": null
}
```

Час передається рядком ISO 8601 у UTC.

Створюється резерв, reserved збільшується на quantity.
onHand не змінюється.

Збереження резерву, зміна залишку та фіксація ключа
ідемпотентності виконуються як одна неподільна операція.
Одночасні запити не можуть зарезервувати більше доступного залишку.

#### Повторні запити

Ключ ідемпотентності перевіряється в межах поточного користувача.

- Однакові ключ, productId і quantity:
  повертається 200 та наявний резерв у його поточному стані.
  Новий резерв не створюється, залишки не змінюються.
- Однаковий ключ, але інші productId або quantity:
  повертається 409 / IDEMPOTENCY_CONFLICT.
- Новий ключ означає нову спробу створення резерву.
- Однакові ключі різних користувачів не конфліктують.
- Одночасні однакові запити створюють лише один резерв.
- Ключ успішної операції зберігається й після скасування
  або видачі резерву. У межах ЛР2 автоматично не видаляється.

Перевірка сесії та ролі виконується і для повторних запитів.
Для вже виконаної операції достатність залишку повторно не перевіряється.

#### Помилки

| Статус | code | Причина |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | Некоректне тіло запиту або Idempotency-Key |
| 401 | UNAUTHENTICATED | Немає чинної сесії |
| 403 | FORBIDDEN | Роль не дозволяє створювати резерв |
| 404 | PRODUCT_NOT_FOUND | Товар не існує |
| 409 | INSUFFICIENT_STOCK | Недостатня доступна кількість |
| 409 | IDEMPOTENCY_CONFLICT | Ключ уже використано з іншими даними |
| 503 | SERVICE_UNAVAILABLE | Недоступне необхідне сховище |

Відхилені запити та повністю відкочені операції
не займають ключ ідемпотентності.

### GET /reservations

Доступ: користувач або працівник із чинною сесією.

Тіло запиту: відсутнє.

Правила доступу:
- USER отримує лише власні резерви всіх статусів.
- WORKER отримує активні резерви всіх користувачів.
- Власник і обмеження за роллю визначаються сервером.

Успіх: 200.
Повертається масив резервів.
Сортування: createdAt за спаданням, за однакового часу - id за спаданням.
Якщо відповідних резервів немає, повертається порожній масив [].

Кожен елемент містить:
- id, userId, productId, quantity, status;
- createdAt, closedAt, issuedById;
- product - короткі дані товару: id, articleCode, name.

Приклад відповіді:

```json
[
  {
    "id": 15,
    "userId": 2,
    "productId": 1,
    "quantity": 3,
    "status": "ACTIVE",
    "createdAt": "2026-10-17T12:00:00.000Z",
    "closedAt": null,
    "issuedById": null,
    "product": {
      "id": 1,
      "articleCode": "ITEM-001",
      "name": "Клавіатура"
    }
  }
]
```

Помилки:
- 401 / UNAUTHENTICATED - немає чинної сесії;
- 503 / SERVICE_UNAVAILABLE - недоступне необхідне сховище.

Перегляд не змінює резерви та залишки.

### GET /reservations/:id

Доступ: власник резерву або працівник із чинною сесією.

Параметр шляху:
- id - ідентифікатор резерву, записаний додатним цілим числом.

Тіло запиту: відсутнє.

Правила доступу:
- USER може переглядати лише власний резерв.
- WORKER може переглядати будь-який резерв.
- Перегляд конкретного резерву дозволений у будь-якому статусі.

Успіх: 200.
Повертається один об’єкт тієї самої структури,
що й елемент відповіді GET /reservations.

Помилки:
- 400 / VALIDATION_ERROR - некоректний id;
- 401 / UNAUTHENTICATED - немає чинної сесії;
- 403 / FORBIDDEN - користувач звертається до чужого резерву;
- 404 / RESERVATION_NOT_FOUND - резерв не існує;
- 503 / SERVICE_UNAVAILABLE - недоступне необхідне сховище.

Перегляд не змінює резерв і залишки.

### POST /reservations/:id/cancel

Доступ: USER, який є власником резерву.
Працівник не може скасовувати резерви.

Параметр шляху:
- id - ідентифікатор резерву, записаний додатним цілим числом.

Тіло запиту: відсутнє.
Idempotency-Key не потрібний.

Успіх: 200.
Повертається об’єкт резерву тієї самої структури,
що й у GET /reservations/:id.

Поведінка залежно від поточного статусу:
- ACTIVE:
  статус змінюється на CANCELLED;
  reserved зменшується на quantity;
  closedAt встановлюється сервером.
- CANCELLED:
  повертається поточний резерв без повторних змін.
- ISSUED:
  повертається 409 / INVALID_RESERVATION_STATUS.

onHand не змінюється.
issuedById залишається null.
Зміна резерву та залишку виконується неподільно.

Помилки:
- 400 / VALIDATION_ERROR - некоректний id;
- 401 / UNAUTHENTICATED - немає чинної сесії;
- 403 / FORBIDDEN - роль не дозволяє операцію або резерв чужий;
- 404 / RESERVATION_NOT_FOUND - резерв не існує;
- 409 / INVALID_RESERVATION_STATUS - резерв уже виданий;
- 503 / SERVICE_UNAVAILABLE - недоступне необхідне сховище.

Права перевіряються також для повторного запиту.
Повторне скасування не змінює closedAt і залишки.

### POST /reservations/:id/issue

Доступ: WORKER із чинною сесією.

Параметр шляху:
- id - ідентифікатор резерву, записаний додатним цілим числом.

Тіло запиту: відсутнє.
Idempotency-Key не потрібний.

Видається вся кількість із резерву.
Часткова видача не підтримується.

Успіх: 200.
Повертається об’єкт резерву тієї самої структури,
що й у GET /reservations/:id.

Поведінка залежно від поточного статусу:
- ACTIVE:
  статус змінюється на ISSUED;
  onHand і reserved зменшуються на quantity;
  closedAt встановлюється сервером;
  issuedById визначається за поточною сесією працівника.
- ISSUED:
  повертається поточний резерв без повторних змін.
- CANCELLED:
  повертається 409 / INVALID_RESERVATION_STATUS.

Зміна резерву та залишку виконується неподільно.

Помилки:
- 400 / VALIDATION_ERROR - некоректний id;
- 401 / UNAUTHENTICATED - немає чинної сесії;
- 403 / FORBIDDEN - роль не дозволяє видачу;
- 404 / RESERVATION_NOT_FOUND - резерв не існує;
- 409 / INVALID_RESERVATION_STATUS - резерв уже скасований;
- 503 / SERVICE_UNAVAILABLE - недоступне необхідне сховище.

Права перевіряються також для повторного запиту.
Повторна видача не змінює залишки, closedAt та issuedById,
навіть якщо запит надіслав інший працівник.

### Одночасне скасування та видача

Якщо скасування й видача одного активного резерву
виконуються одночасно, успішним може бути лише один перехід.

Інша операція отримує 409 / INVALID_RESERVATION_STATUS.
Залишки змінюються лише відповідно до успішного переходу.

Одночасні повтори однієї операції не спричиняють
повторної зміни залишків.
