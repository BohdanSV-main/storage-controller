# Обробка збоїв PostgreSQL

Якщо необхідне сховище недоступне, API повертає HTTP 503:

```json
{
  "error": {
    "code": "SERVICE_UNAVAILABLE",
    "message": "Required storage is temporarily unavailable."
  }
}
```

Спільний обробник у `src/plugins/error-handler.ts` працює для помилок маршрутів і сховища сесій. SQL, адреса БД та стек викликів не потрапляють у відповідь

Розпізнаються коди Prisma P1001, P1002, P1008, P1017, P2024, P2037,
а також P2034 після вичерпання трьох спроб Serializable-транзакції.
Для прямих помилок адаптера розпізнаються DatabaseNotReachable, ConnectionClosed та SocketTimeout. Інші непередбачені помилки повертають 500 / INTERNAL_ERROR із загальним повідомленням. Валідація й бізнес-помилки зберігають свої HTTP-коди.

## Відновлення та повторні запити

- Під час збою читання сесії повертається 503, а не 401.
- Невдала операція logout не повідомляє про успішний вихід. Після відновлення БД її можна повторити.
- HTTP-запити автоматично не повторюються. Після збою під час створення бронювання клієнт має використати той самий Idempotency-Key і ті самі дані: відповідь 503 сама по собі не доводить, що транзакція не встигла зафіксуватися.
- Після відновлення з’єднання нові запити обслуговуються тим самим процесом застосунку.
- `/health` без cookie перевіряє, що HTTP-застосунок живий; це не перевірка доступності БД. Запит із cookie може звернутися до сховища сесій і отримати 503.
- Якщо початкове підключення до БД під час запуску не вдалося, сервер не починає слухати порт і завершується з помилкою. Після відновлення БД його треба запустити знову.

## Перевірки

`npx vitest run src/plugins/error-handler.test.ts` перевіряє класифікацію помилок, безпечні відповіді 503/500, відмову операцій сховища сесій та відновлення після імітованого збою. Це перевірка обробника з підставленими помилками, а не відключення реальної PostgreSQL.

`npm run test:db` перевіряє транзакції та відкат записів на реальній БД.
