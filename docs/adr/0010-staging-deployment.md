# ADR-0010: Розгортання staging на Render

Статус: прийнято  
Дата: 26.11.2026 [01:47]

## Контекст і проблема

Аппка має бути доступна з інтернету. Після мерджа в `main` нова версія має розгортатися автоматично. GitHub Actions запускає перевірки без доступу до staging-БД і без SSH.

## Критерії вибору

- Деплой Docker-образу після успішного CI.
- Перемикання трафіку після перевірки готовності.
- Мінімум ручного обслуговування сервера.

## Розглянуті варіанти

### Варіант 1. Render

- Переваги: збирає образ із Dockerfile, підтримує деплой після CI та перевірку готовності за HTTP.
- Недоліки: 700 хвилин роботи на місяць, після довгого простою хвилина на перезапуск.

### Варіант 2. VPS із Docker

- Переваги: повний контроль над сервером, мережею та PostgreSQL.
- Недоліки: потрібно самостійно налаштувати HTTPS, оновлення системи й перемикання трафіку між версіями.

### Варіант 3. Azure App Service

- Переваги: підтримує Docker. Слоти розгортання дозволяють прогріти нову версію перед перемиканням трафіку.
- Недоліки: для використання слотів потрібен тариф Standard або вище. Гроші шкода.

## Рішення

Обрав Render. Один Web Service запускає Fastify та віддає зібраний React з того самого домену. Для CD гілка `main`, режим деплою `After CI Checks Pass`, перевірка готовності `/ready`.

## Наслідки

Перед стартом API контейнер застосовує міграції Prisma. Seed запускається окремо.

## Перевірка

Після мерджа звірити SHA у `main` із відповіддю публічного `/version`. Мають співпадати.
