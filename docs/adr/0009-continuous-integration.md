# ADR-0009: Вибір CI для перевірки pull request

Статус: прийнято  
Дата: 23.11.2026 [20:17]

## Контекст і проблема

Код і pull request зберігаються на GitHub. Перед мерджем у main потрібен результат перевірки на чистому середовищі. 

## Критерії вибору

- Блокування мерджа, якщо обов’язкова перевірка впала.
- Запуск наявних npm-команд, PostgreSQL і Chromium.
- Ізоляція тестової БД від staging і production.
- Мінімум роботи з обслуговування CI.

## Розглянуті варіанти

### Варіант 1. GitHub Actions

- Переваги: результати видно в PR, перевірки можна зробити обов’язковими для main. GitHub надає runner, а PostgreSQL можна запустити як сервіс на час job.
- Недоліки: workflow прив’язаний до GitHub Actions. Захист main потрібно окремо налаштувати в репозиторії.

### Варіант 2. Jenkins

- Переваги: повний контроль над runner, середовищем. Jenkins може передавати в GitHub результати.
- Недоліки: потрібно розгорнути й оновлювати Jenkins.

## Рішення

Обрав GitHub Actions. Для цього проєкту достатньо Ubuntu runner і тимчасової PostgreSQL 17
Для Conventional Commits обрав commitlint із готовими правилами

## Наслідки

Для мерджа в main мають пройти `backend`, `frontend`, `db` і `commits`.
## Перевірка

Конфігурація CI зберігається в `.github/workflows/ci.yml`, правила комітів у `commitlint.config.js`.
