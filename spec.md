# Специфікація застосунку: Сервіс для резервування товарів для отримання зі складу

## 1. Ідея

Для мене цей сервіс вигладає так: юзер перевіряє і резервує потрібну кількість товару, працівник складу фіксує видачу. Ціль це вести облік товарів та залиштів на складі.

## Можливості

Користувач може переглядати каталог і доступну кількість товару, створити резерв на певний товар, переглянути всі свої резерви та скасувати активну резервацію.

Працівник має можливість переглянути активну резервацію та підтвердити видачу товару після чого товар буде списаний зі складу.

## Межі проєкту

Застосунок адаптований під Один склад, цілі значення одиниць товару. Відстуня оплата, доставка кошик та автоматичне скасування за таймером.

## Дані та зв'язки

### Сутності

| Сутність    | Призначення                                               | Поля                                                                                                                                                                                                                   |
| ----------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User        | Потрібно щоб визначити чиї резервації та права працівника | id: індентифікатор, name: ім'я, email: пошта, role: роль                                                                                                                                                               |
| Product     | Описує товар                                              | id: індентифікатор, articleCode: артикул продукту, name: назва товару, desc: опис товару                                                                                                                               |
| Stock       | Поточна кількість залишку                                 | productId: індентифікатор товару, reserved: зарезервована кількість, onHand: наявна кількість                                                                                                                          |
| Reservation | Показує резервування товару та його статус                | id: індентифікатор, userId: індентифікатор власника, productId: товар, quantity: кількість, status: стан, createdAt: час створення резервації, closedAt: час скасування issuedById: працівник котрий підтвердив видачу |

### Зв'язки

Кожен користувач має багато резервів; кожен резерв має власника
Товар може бути в багатьох резервах; кожен резерв стосується одного товару
Кожен товар має один запис залишку
Працівник може підтвердити видачу багатьох резервів; до видачі товару атрибут isssuedById порожній.

### Сценарії та зміни даних

| Сценарій          | Що перевіряємо                                                                          | Зміна даних                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Створення резерву | Товар має існувати. Кількість має бути додатньою, але не перевищувати доступний залишок | Створюється активний резерв; У Stock значення reserved збільшується на кількітсь у самому резерві; onHand не змінюється         |
| Скасування        | Резерв активний і належить користувачу                                                  | Статус стає скасованим; reserved зменшується на кількість у резерві; onHand не змінюється; closedAt записується час скасування  |
| Видача            | Дію виконує працівник; резерв активний                                                  | Статус стає виданим; записується працівник видавший товар, та час видачі; reserved та onHand зменшується на кількість у резерві |

## Компоненти та взаємодія

| Модуль          | Відповідальність                                                                                   | Взаємодія                                                                              |
| --------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Каталог товарів | Перелік і опис товарів                                                                             | Використовує облік залишків для показу доступної кількості                             |
| Облік залишків  | показує фізичну, зарезервовану та доступну кількість товару; відповідає за коректні зміни залишків | Використовується каталогом і резервуванням                                             |
| Резервування    | Створює резерви, показує власні резерви користувача, обробляє скасування та видачу                 | Звертається до каталогу для перевірки товару та до обліку залишків для зміни кількості |

У ЛР1 src/index.ts запускає сервер, src/app.ts створює застосунок і реєструє /health, src/app.test.ts перевіряє його працездатність.
Контролери, сервіси та репозиторії для каталогу, залишків і резервування будуть додаватися під час реалізації відповідних сценаріїв.

З технічного боку HTTP-запити обробляють контролери, сценарії та бізнес правила виконують сервіси, читання і збереження даних - репозиторій. Зміна резерву та пов'язаного залишку виконується як одна неподільна операція.


## Критерії прийняття прото-проєкту (ЛР1)

У ЛР1 реалізуються мінімальний сервер, smoke-тест та інструменти перевірки; каталог, резервування, видача й робота з БД поки лише проєктуються.

- Застосунок запускається за інструкцією в README; запит GET /health повертає код 200 і "status": "ok".
- Структура коду відповідає описаному поділу відповідальності.
- Команда make check запускає перевірку форматування, лінтер, smoke-тест і збірку. усі перевірки проходять.
- Git hooks автоматично запускають погоджені перевірки перед commit та push. збережено доказ блокування дії з помилкою.
- У standards/ описані формат специфікації, шаблон ADR, Definition of Done та перелік перевірок.
- Ключові рішення задокументовані в ADR; виконано аудит структури та залежностей із поясненням знайдених проблем і виправлен.
