# Специфікація застосунку: Сервіс для резервування товарів для отримання зі складу

## 1. Ідея

Сервіс обліку та резервування товарів одного складу. Користувач резервує потрібну кількість товару, працівник підтверджує видачу, а застосунок підтримує коректний фізичний і доступний залишок.

## Можливості

Вхід за email і паролем для підготовлених облікових записів.
Користувач може вийти та переглянути дані свого облікового запису.
Права й власник резерву визначаються сервером.
Користувач: перегляд каталогу й доступного залишку, створення резерву, перегляд власних резервів усіх статусів, скасування власного активного резерву.
Працівник: перегляд каталогу, активних резервів і деталей резерву, підтвердження видачі. Власні резерви не створює та чужі не скасовує.

## Межі проєкту

Застосунок адаптований під Один склад, цілі значення одиниць товару. Товари, початкові залишки та облікові записи завантажуються підготовленими даними. Реєстрація, відновлення пароля, зміна ролей, редагування каталогу, оплата, доставка, кошик, кілька складів
і автоматичне скасування за таймером не входять до ЛР2.

## Дані та зв'язки

### Сутності

| Сутність | Основні поля |
| --- | --- |
| User | id, name, email, passwordHash, role |
| Product | id, articleCode, name, desc |
| Stock | productId, onHand, reserved |
| Reservation | id, userId, productId, quantity, status, createdAt, closedAt, issuedById |
| Session | id, data, expiresAt |
| ReservationIdempotencyKey | userId, key, productId, quantity, reservationId |

onHand - фізичний залишок включно з резервами;
reserved - зарезервована кількість.
Статуси: ACTIVE, CANCELLED, ISSUED.
closedAt - час скасування або видачі;
issuedById - працівник,який видав товар. До відповідної події ці поля порожні.

### Зв'язки

User 1:N Reservation - власник;
Product 1:N Reservation;
Product 1:1 Stock. issuedById посилається на User у ролі працівника.

### Сценарії та зміни даних

| Сценарій | Умови | Результат |
| --- | --- | --- |
| Вхід / вихід | Правильні облікові дані для входу | Сервер розпізнає користувача; після виходу попередній сеанс не дає доступу |
| Перегляд каталогу | Користувач або працівник увійшов | Товари та доступна кількість; залишки не змінюються |
| Перегляд резервів | Перевірені роль і власник | Користувач бачить власні резерви; працівник - активні для видачі та деталі резерву |
| Створення резерву | Користувач; товар існує; кількість додатна, ціла й доступна | Створюється ACTIVE; reserved збільшується на quantity; onHand не змінюється |
| Скасування | Власник резерву; статус ACTIVE | Статус CANCELLED; reserved зменшується на quantity; записується closedAt |
| Видача | Працівник; статус ACTIVE | Статус ISSUED; onHand і reserved зменшуються на quantity; записуються issuedById та closedAt |

Доступна кількість: available = onHand - reserved.
Завжди виконується 0 <= reserved <= onHand.
ID та quantity у запитах - цілі числа від 1 до 2 147 483 647 включно.
Залишки - цілі числа від 0 до 2 147 483 647. Значення за межами допустимого
діапазону запиту повертають 400 / VALIDATION_ERROR до звернення до репозиторію резервів.
Зміни резерву та залишку виконуються неподільно.
Одночасні запити не можуть зарезервувати більше доступної кількості.

## Компоненти та взаємодія

Модулі: облікові записи й доступ, каталог, залишки, резервування.
Каталог читає залишки; резервування перевіряє товар і змінює залишки;
модуль доступу визначає користувача та права.

HTTP-обробники => сервіси сценаріїв => репозиторії.
Спочатку сховище в пам'яті, потім БД.
Мінімальний вебінтерфейс додається після API та інтеграції БД.

src/index.ts підключає PostgreSQL, сховище сесій та модулі автентифікації,
каталогу й резервування. src/app.ts створює застосунок, налаштовує сесії,
CSRF та обробку помилок і реєструє /health та /version.

З технічного боку HTTP-запити обробляють контролери, сценарії та бізнес правила виконують сервіси, читання і збереження даних - репозиторій. Зміна резерву та пов'язаного залишку виконується як одна неподільна операція.

### Повторні запити та помилки

Операції зміни залишків використовують рівень ізоляції Serializable. Тобто при конфлікті транзакцій P2034 виконується до трьох спроб із затримкою, а інші помилки автоматично не повторюються.

HTTP-коди:
- 400 - неправильні дані запиту;
- 401 - відсутня або прострочена сесія;
- 403 - недостатні права чи порушення перевірки Origin;
- 404 - товар або резерв не знайдено;
- 409 - недостатній залишок, конфлікт ключа або заборонений перехід статусу;
- 503 - недоступне сховище або вичерпані повторні спроби транзакції;
- 500 - непередбачена внутрішня помилка.

Збій читання сесії повертає 503, а не 401.
Відповіді не містять SQL, секретів чи стеку викликів.

HTTP-контракт: docs/api.md.
Поведінка при збоях: docs/database-failures.md.

## Критерії прийняття ЛР2

HTTP-обробники приймають запити, сервіси виконують бізнес-сценарії, репозиторії забезпечують доступ до даних.
Вебінтерфейс Каміра реалізований окремим React-застосунком у папці frontend/.

- Основні сценарії продемонстровані спочатку на даних у пам'яті, потім на реальній БД; результати перевірок збережені.
- Вхід, вихід, перевірка ролей і доступу до власних резервів працюють.
- Створення, скасування та видача змінюють дані за описаними правилами.
- Дані БД зберігаються після перезапуску застосунку.
- Помилка всередині операції не залишає часткових змін; конкурентні резервування не перевищують залишок.
- Повторні запити не створюють дублікати й не змінюють залишки повторно.
- Помилкові дані та збої БД дають контрольовані відповіді.
- README дозволяє підготувати БД, початкові дані, запустити застосунок.
